# LinQ Guard — видеоконтроль нарушений ТБ на ускорителе LinQ

Веб-сервис для производства: по видео с камер находит опасное поведение людей, подтверждает нарушение
во времени и присылает **одно** оповещение с кадром-доказательством. Журнал событий служит доказательной
базой для службы охраны труда, аналитика показывает, где и когда нарушают чаще всего.
Нейросети — архитектуры из списка поддерживаемых SDK LinQ, постпроцессинг общий для GPU и TPU.

Кейс хакатона «Открой Моспром», постановщик — LinQ.

## Telegram-бот и мини-апп: реакция на инцидент

Промбез — это онлайн и быстрая реакция, поэтому главный канал — бот **@linq_control_bot** с мини-аппом.
Роль определяется по Telegram ID (`configs/roles.yaml`); в демо-режиме роль выбирают сами (`/start`, `/role`).

| Роль | Что получает |
|---|---|
| Рабочий | в конце смены — свои нарушения за смену (карточка «Итоги смены» и CSV); находит себя в мини-аппе по фото лица; сводка «кто где нарушал» |
| Оператор | живая лента всех нарушений; любое нарушение можно «Передать начальнику смены» с комментарием; критичные тревоги — для сведения |
| Начальник смены | мгновенно — критичные нарушения (падение, огонь, техника рядом с человеком) карточкой с кадром и сроком; «▶️ Видео» — ролик ±4 с для проверки; «Принял» → «Устранено» с коротким отчётом; лента, люди, лайв-загрузка записи, CSV, закрытие смены |
| Руководитель | уведомление, если тревогу не закрыли в срок (30 мин, настраивается), «Запросить отчёт» и «▶️ Видео»; показатели смены и время реакции по каждому начальнику смены. Сам тревоги не закрывает |

- **Сроки и отчётность:** у каждой тревоги срок устранения; время до «Принял» и до «Устранено», доля закрытых в срок
  и разбивка по начальникам смены — в /shift, в мини-аппе, в отчёте смены и в CSV по тревогам.
- **Опознание нарушителей по лицу** — YuNet + SFace (OpenCV Zoo, Apache-2.0/MIT): каждое нарушение человека
  привязывается к профилю «Сотрудник №N» с фото лица; имена не хранятся, профиль связывается с Telegram ID самим рабочим.
- **Лайв-режим** — запись, загруженная в мини-апп, идёт в реальном времени как отдельная камера со всеми правилами;
  тревоги из неё уходят в бот так же, как с настоящих камер.
- **Чистый чат:** тревога правится на месте («👀 Принял», «✅ Устранено …») и через 2 минуты после закрытия удаляется,
  служебные сообщения и ролики для проверки удаляются сами; у каждой роли своё меню команд, /clear.
- Мини-апп открывается по HTTPS через туннель (`tools/public_url.sh`); снаружи доступны только мини-апп и его API.
  Токен бота — `tools/set_bot_token.sh` (в файл на сервере, не в репозиторий). Деплой — [docs/DEPLOY.md](docs/DEPLOY.md).

**Видео (релиз v1.1.0):** скринкасты мини-аппа по всем ролям и дашборда, нарезка нарушений с разметкой системы,
демо-смена со всеми нарушениями для лайв-режима (`tools/factory_videos.sh`, `tools/screencast.py` пересобирают их).

Код: `api/shift.py` (роли, смены, тревоги, эскалация, отчёты), `api/telegram.py` (бот), `api/tg_routes.py` (API мини-аппа),
`api/people.py` + `engine/faces.py` (лица), `api/static/tg/` (мини-апп).

## Результаты

**Падение (UR Fall, 30 падений + 40 записей обычной активности).** Параметры подбирались на нечётных записях,
цифры — на чётных, которых система не видела: правило — recall 40%, precision 86%, F1 0,55, одна ложная тревога
на 20 записей обычной активности; классификатор на позе — recall 53%, precision 57%, F1 0,55. В работе правило:
в кейсе точность важнее числа сценариев. Ограничение набора — камера в углу комнаты, 320×240.
Сел, присел или встал на колени — не падение: после резкого опускания корпус должен лежать (наклон от вертикали
50° и больше); на отложенной половине recall и precision от этого не изменились, ложных на всём наборе стало меньше.

**Огонь.** Открытый детектор путает пламя с лампами, бликом сварки, жёлтым жилетом и оранжевой каской. Поэтому огонь
засчитывается, только если в рамке не меньше 20% «огненных» пикселей и не больше 40% белого блика и рамка не лежит
на голове или корпусе человека, а сноп искр от болгарки (вытянутая полоса или россыпь мелких штрихов) отсеивается
по форме рамки и доле контуров; подтверждение — 1 с (пламя мерцает, детектор ловит его через кадр).
В демо-смене остался только горящий баллон; лампы, блики и искры ушли.

**Каски и жилеты (jhboyo/ppe-dataset, 2751 тестовое изображение, не участвовали в обучении).** Открытая модель
с Hugging Face — mAP50 0,29, голову без каски находит в 5% случаев. Дообученная нами YOLOv8s — mAP50 0,93
(каска 0,94, голова без каски 0,91, жилет 0,94; при рабочем пороге precision 0,92 / recall 0,85 на головах без каски).
Оговорка: тест из того же набора, что и обучение; на кадрах заказчика модель нужно дообучить. Правило «нет каски»
работает на нашей модели; «нет жилета» — пока на открытой: только у неё есть класс «без жилета».

**Перенос на LinQ.** Поза после квантования находит 99% людей исходной модели при IoU 0,97 и сдвиге точек
скелета 2,5% роста. Открытый детектор СИЗ — 88% объектов при 5% лишних (калибровка по кадрам с объектами
и дообучение порогов квантования), погрузчик — 85% / 8%. Наша YOLOv8s квантуется хуже: на её тестовых снимках
70% объектов при 6% лишних, на кадрах демо-камер — 55% / 19% (там много пограничных детекций). Перебрали калибровку
на обучающих снимках, дообучение порогов, перцентиль, вынос ветки классов на CPU — потери не в логитах классов,
а раньше по сети; это следующая задача. Подробности — экраны «Качество» и «LinQ».

**Скорость (сервер с RTX 3060, 1 кадр 640×640).** Поза: GPU 4,5 мс, до 218 кадров/с в 4 потока; CPU 111 мс, 19 кадров/с.
Разбор 9-минутной записи смены всеми семью моделями — в 1,8 раза быстрее реального времени, рядом при этом работают 7 камер
(26 роликов: огонь, падение, каски, жилеты, курение, телефон, задымление).

## Архитектура

```
Источники ──► Детекторы (ONNX / TPU LinQ) ──► Постпроцессинг YOLO (numpy) ──► Трекер
   │                                                                          │
   │          Правила-плагины по зонам и расписаниям ◄────────────────────────┘
   │                          │
   │                Менеджер событий: окно подтверждения, доля кадров, удержание, кулдаун, склейка ID
   │                          │
   └──► Веб (FastAPI): кадры по WebSocket, лента, галерея, журнал (SQLite), аналитика, зоны, метрики
```

- `engine/postprocess.py` — letterbox и декодирование выхода YOLOv8/YOLO11 (detect и pose) с NMS на numpy.
  Тот же код обрабатывает выход хвоста модели после TPU.
- `engine/backends.py` — `OnnxBackend` (CUDA/CPU) и `LinqTpuBackend` (pytpu + хвост ONNX на CPU).
- `engine/rules/` — нарушения. Новое нарушение — новый класс с декоратором `@register`, ядро не меняется.
- `engine/events.py` — превращает покадровые сигналы в события; подробности в docstring.
- `configs/cameras/*.yaml` — камеры, модели, зоны, правила, расписания, калибровка пола.
- `api/` — веб-сервис и интерфейс (без сборки фронтенда).

```bash

uv pip install --index-url https://download.pytorch.org/whl/cu124 torch torchvision
```

## LinQ

- Все модели экспортируются в ONNX с фиксированным входом 1×3×640×640 — требование SDK.
- YOLOv8n-pose есть в списке поддерживаемых моделей SDK; детекторы — того же семейства YOLOv8.
- Голова YOLO отрезается `get_sub_model`: TPU считает сеть до decode, хвост и NMS выполняет CPU тем же кодом.
- Калибровка квантования — на реальных кадрах камер, а не на случайных данных из примера SDK.
- Замеры: экран «LinQ» показывает задержку каждой модели по этапам (препроцессинг, инференс, постпроцессинг).

## Стенд LinQ: как работает сейчас

Сервис, Telegram-бот и мини-апп развёрнуты **на стенде организаторов** — в контейнере Jupyter рядом с TPU;
дашборд с ноутбука — через VPN и прокси Jupyter (`tools/stand_tunnel.py` → http://127.0.0.1:8765),
мини-апп — через HTTPS-туннель Cloudflare со стенда (`tools/stand_public.sh`).

```
камеры ─► letterbox ─► шлюзы TPU (пул процессов, engine/tpu_gateway.py) ─► RabbitMQ tpu.direct/input ─► воркеры LinQ (16)
                                                                          ◄─ выходы последних свёрток головы YOLO
           хвост ONNX на CPU (decode, NMS) ─► трекер ─► правила ─► события ─► дашборд / Telegram
```

- **Облачный TPU стенда** (`LinqCloudBackend`): на стенде нет `/dev/tpu`, программы `.tpu` из `/auto/cache/<логин>/`
  выполняет облачный воркер через RabbitMQ. В машине с ускорителем тот же код берёт `LinqTpuBackend` (pytpu).
- **Склейка моделей камеры в одну программу** (`linq/fuse_models.py`, `linq/compile_fused.py`, `LinqFusedBackend`):
  кадр уходит на ускоритель один раз вместо 2–3 — на стенде ×1,4–2,6 кадров/с, на чипе 13,2 мс вместо 8,5 + 8,1.
- **Сырой режим TPU** (`engine/tpu_raw.py`, `LINQ_TPU_RAW=1`): кадр и выходы в int8-раскладке ускорителя кодеком SDK —
  трафик 4,9 → 1,6 МБ туда и 3,9 → 1,1 МБ обратно, выходы бит в бит как в float32. На стенде выключен: упаковка
  упирается в квоту CPU контейнера; выигрывает там, где узкое место — канал до ускорителя.
- **Демо-камеры и демо-смена** заранее прогнаны через TPU с моделями и порогами релиза (`tools/precompute_tpu.py`):
  ролик идёт в реальном темпе с этими детекциями (`LINQ_REPLAY=1`), трекер, правила и тревоги — вживую.
  Загруженная в лайв-режим запись узнаётся по отпечатку содержимого; любая другая считается на TPU в реальном времени.

### Замеры на стенде (24.10)

| Модель | на чипе (отчёт воркера) | весь запрос через стенд |
|---|---|---|
| поза YOLOv8n-pose | 8,5 мс (~117 кадров/с) | ~310 мс |
| погрузчик | 8,1 мс | ~300 мс |
| телефон и транспорт YOLOv8s | 13,5 мс | ~400 мс |
| склейка поза + погрузчик | 13,2 мс | ~410 мс |

97% времени запроса — инфраструктура общего стенда (очередь, пересылка ~5 МБ кадра, сериализация, квота CPU
контейнера 1,5 ядра). С ускорителем в том же сервере один чип даёт ~75–120 кадров/с на модель.

Потери квантования на демо-камерах (детекции TPU против FP32-модели на тех же ~640 кадрах, `eval/compare_tpu_fp32.py`):

| Класс | найдено TPU | лишние |
|---|---|---|
| человек | 98% | 3% |
| телефон | 90% | 3% |
| сигарета | 88% | 32% |
| погрузчик | 83% | 4% |
| без жилета | 65% | 15% |
| **голова без каски (наша модель касок)** | **1%** | — |

Модель касок после квантования теряет голову без каски при любых настройках (перебор — `linq/ppe2_quant_sweep.py`:
12–19% в эмуляторе), поэтому на стенде она считается в FP32 на CPU (`LINQ_CPU_MODELS=ppe2`) — «нет каски»
совпадает с FP32 на 100%. Остальные шесть моделей — на TPU.

### Запуск на стенде

## Ограничения

- Демо работает на видеофайлах; на объекте источники — RTSP с IP-камер.
- Демо-ролики идут по кругу: нарушение записывается в журнал на первом проходе, на следующих — только снова подсвечивается как активное.
  После перезапуска сервиса первый круг записывается заново; чистый старт демо — `tools/demo_reset.sh` (старый журнал сохраняется).
- Без калибровки пола расстояния и скорости считаются в ростах человека, а не в метрах.
- Узкие детекторы с Hugging Face обучены на чужих данных; на объекте их нужно дообучить на кадрах своих камер.
- Стенд LinQ: квота CPU контейнера 1,5 ядра и общая очередь TPU на все команды — живые камеры 1–4 кадра/с;
  демо-камеры поэтому прогнаны через TPU заранее. Адрес быстрого туннеля Cloudflare меняется при перезапуске.
- Модель касок на стенде — FP32 на CPU (квантование ломает класс «голова без каски»); YOLO11-сигарета не склеивается
  с другими моделями в одну программу.
