# Карта кода — памятка к защите

Как отвечать на вопросы по коду: путь кадра от камеры до оповещения, где что лежит и почему сделано так.

## Путь одного кадра

1. **Источник** — `api/workers.py: VideoWorker` читает видеофайл или RTSP через OpenCV, берёт каждый N-й кадр,
   чтобы анализ шёл с частотой `analysis_fps` (обычно 5 кадров/с). Для файлов держит темп реального времени.
2. **Подготовка кадра** — `engine/postprocess.py: letterbox`: вписать в 640×640 с серыми полями, BGR→RGB, /255.
   Делается один раз на кадр и переиспользуется всеми моделями (`engine/pipeline.py: detect`).
3. **Нейросети** — `engine/detector.py: Detector` вызывает бэкенд из `engine/backends.py`:
   - `OnnxBackend` — ONNX Runtime на GPU или CPU (сейчас на vast);
   - `LinqTpuBackend` — программа `.tpu` на ускорителе LinQ через `pytpu`, хвост модели — ONNX на CPU.
   Переключение: переменная окружения `LINQ_BACKEND=tpu`.
4. **Постпроцессинг** — `engine/postprocess.py: decode`: выход YOLO (1, C, N) → рамки, классы, точки скелета,
   NMS на numpy. Один код для GPU и TPU — поэтому поведение на LinQ не отличается.
5. **Трекинг** — `engine/tracking.py: IouTracker`: сопоставляет рамки между кадрами, у каждого человека свой ID
   и история за ~30 секунд.
6. **Правила** — `engine/rules/`: по зонам камеры (`configs/cameras/*.yaml`) каждое правило смотрит на трек и
   говорит «в этом кадре нарушение есть / нет». Правила ничего не знают про оповещения.
7. **Менеджер событий** — `engine/events.py`: превращает покадровые сигналы в события. Подтверждение, только если
   нарушение длится `confirm_s` и в окне не меньше 70% кадров с сигналом. Одно событие на нарушение, пока человек
   в кадре; склейка при смене ID трека; огонь и дым — одно событие на зону.
8. **Доказательства и журнал** — `api/workers.py: SourceProcessor`: кадр с выделенным нарушителем, ролик ±4 с,
   запись в SQLite (`api/store.py`), рассылка в браузер по WebSocket и, для критичных, в Telegram/вебхук
   (`api/notify.py`). Видеофайл по кругу (демо): новый круг закрывает события прошлого прохода, а повтор уже
   записанного нарушения (тот же тип, зона, место в кадре и в записи) не пишется заново — исходное событие
   снова становится активным (`SourceProcessor.new_pass`, `_replay_target`).

## Режим «Разбор смены»

`api/review.py`: та же цепочка, но запись обрабатывается без паузы между кадрами, быстрее реального времени.
Каждое событие становится роликом (3 с до, всё нарушение до 20 с, 2 с после). Ранг ролика =
вес тяжести × уверенность × (1 + длительность/20). Ответственный проверяет ролики подряд и выгружает отчёт.

## Как добавить новое нарушение

1. Класс в `engine/rules/*.py` с декоратором `@register("тип", "Название")` и методом `evaluate(track, ctx)`.
2. Тип в YAML камеры. Всё остальное — трекер, подтверждение, ролики, журнал, отчёты — работает без изменений.

## LinQ

- `linq/compile_tpu.py`: срез ONNX (`get_sub_model`) по последним свёрткам головы YOLO → калибровка на кадрах
  камер (с упором на кадры с объектами) → `fine_tune_torch` порогов → `compiler.compile_` с пресетом O5 → `.tpu`.
- `linq/verify_quant.py`: квантованная модель в эмуляторе SDK против исходной FP32 на других кадрах:
  сколько объектов находит так же, сколько лишних, IoU, сдвиг точек скелета.
- `linq/bench.py`: задержка и пропускная способность на TPU, GPU и CPU в одном формате.

## Качество

- `eval/metrics.py`: P/R/F1 по событиям, взвешенный по тяжести recall (пропуск критичного в 10 раз дороже),
  взвешенное покрытие времени нарушения тревогой, ложные тревоги в час, задержка тревоги, итоговый балл.
- `eval/urfall.py`: оценка падений на открытом размеченном наборе UR Fall (30 падений + 40 записей обычной активности).
- `eval/compare_ppe.py`: открытая и дообученная модели СИЗ на одной тестовой части — AP50 по классам и P/R при рабочем пороге.
- `tests/`: подтверждение и подавление повторов, склейка ID, расписание зон, декодирование YOLO, сближение с учётом
  глубины, метрики, оповещения. Запуск: `python -m pytest`.

## Частые вопросы

- **Почему не одна большая модель?** Узкие детекторы можно включать по участкам (на складе — погрузчики, на
  площадке — огонь), это экономит TPU. На LinQ каждая модель — отдельная программа, несколько программ работают
  на одном устройстве.
- **Почему YOLOv8?** Семейство из списка поддерживаемых моделей SDK LinQ (там есть yolov8n_pose), статичный вход
  640×640, свёрточная сеть хорошо квантуется.
- **Как боретесь с ложными?** Подтверждение во времени, доля кадров, пороги уверенности по моделям, минимальный
  рост человека для СИЗ, глубина для сближения, исключения по зонам и расписаниям, отметки оператора.
- **Что будет на настоящем объекте?** RTSP вместо файлов, калибровка пола по 4 точкам для метров, дообучение
  детекторов на кадрах своих камер — разметка берётся из отметок оператора.
