# LinQ Guard — черновик презентации к защите (25.10)

Регламент держим в ~7 минут: 1 минута проблема, 3 минуты живое демо, 2 минуты LinQ и качество, 1 минута внедрение.
Каждый слайд — один тезис. Цифры только измеренные, рядом с ними — условия замера.

---

## 1. Проблема (30 с)
- Камеры на производстве есть почти везде, но работают как архив: смотрят после травмы.
- Оператор теряет внимание через 20–30 минут, контроль ТБ выборочный.
- **Тезис:** нужна система, которая сама замечает опасное поведение и зовёт человека — быстро и без ложных тревог.

## 2. Решение одной фразой (20 с)
LinQ Guard — веб-сервис на отечественном ускорителе LinQ: камеры → нейросети → правила во времени →
одно оповещение с кадром и роликом → журнал, разбор смены и статистика.

## 3. Два режима, как работают люди (20 с)
- **Live** — только самое опасное (падение, сближение с техникой, огонь): мгновенно мастеру, со звуком, в Telegram.
- **Разбор смены** — всё остальное: вместо суток записи — несколько десятков роликов по категориям, по степени опасности.

## 4. ДЕМО, 3 минуты (самое важное)
1. **Мониторинг** — 7 камер, нарушения подсвечены прямо на кадре; строка обстановки сверху.
   Показать: человек без каски → через 3 с одно событие, а не поток сообщений.
2. **Карточка события** — кадр с выделенным нарушителем, ролик ±4 с, «Подтвердить / Ложное / Передать мастеру».
3. **Разбор смены** — 10 минут записи → 42 ролика, отсортированы по тяжести и уверенности.
   Пройти 3 ролика клавишами A / X, вписать сотрудника, открыть «Отчёт по смене» (печать/PDF).
4. **Камеры и зоны** — нарисовать опасную зону мышкой, включить правило с расписанием 07:55–12:00, сохранить.
   Тепловая карта показывает, где нарушают чаще всего.
5. **Аналитика** — сводка смены текстом с рекомендациями, тепловая карта «день × час».
6. (если позволят) **Вебкамера** — участник падает на мат / подносит телефон к уху → событие в ленте.

Запасной план: записанное видео демо, если стенд или сеть подведут.

## 5. LinQ: использовали правильно (1 мин)
- Все модели — архитектуры из списка поддерживаемых SDK (YOLOv8, поза — прямо `yolov8n_pose`), вход 640×640 статичный.
- Срез головы YOLO (`get_sub_model`): TPU считает всю свёрточную часть, CPU — только раскодирование рамок.
  Один и тот же постпроцессинг на GPU и на TPU — поведение не меняется при переносе.
- Квантование: калибровка на кадрах наших камер (а не на шуме из примера SDK), упор на кадры с объектами,
  дообучение порогов `fine_tune_torch`. Компиляция пресетом O5, все 6 моделей собрались.
- Несколько программ на одном устройстве, модели кадра считаются параллельно.
- **Точность после квантования** (эмулятор SDK против исходной модели, на кадрах, не участвовавших в калибровке):
  поза — 99% людей, IoU 0,97, сдвиг точек 2,5% роста; открытый СИЗ — 88% объектов, 5% лишних; погрузчик — 85% / 8%.
  Наша модель касок квантуется хуже: 70% объектов на своих тестовых снимках, 55% на кадрах демо-камер —
  говорим честно и показываем, что перепробовали (калибровка, дообучение порогов, перцентиль, классы на CPU).
- **Скорость**: таблица «LinQ / GPU / CPU» на экране LinQ. GPU RTX 3060 — поза 4,5 мс (218 к/с в 4 потока); CPU — 111 мс (19 к/с).
  Строку LinQ заполняем замером на стенде (скрипт `linq/bench.py` готов). Если стенда нет — честно говорим.
- Калькулятор: сколько камер тянет один узел при измеренной задержке.

## 6. Качество, по-взрослому (40 с)
- Метрика: P/R/F1 по событиям; **взвешенный recall** — пропуск критичного в 10 раз дороже;
  **покрытие времени** — поздняя тревога хуже ранней; ложные тревоги в час; время до тревоги.
- Падения на открытом наборе UR Fall: пороги подбирали на половине, показываем на другой половине:
  recall 40%, precision 86%, одна ложная тревога на 20 записей обычной жизни. Классификатор — recall 53%, но вдвое больше ложных:
  выбрали правило, потому что ложные тревоги убивают доверие.
- Каски: открытая модель с Hugging Face на нашем тесте (2751 снимок) — mAP50 **0,29**, голову без каски находит в 5% случаев.
  Дообучили YOLOv8s на 10 тыс. изображений за 2 часа — **0,93** (голова без каски 0,91). Оговорка вслух: тест из того же набора,
  на объекте дообучаем на кадрах заказчика — отметки оператора «ложное / подтверждено» и есть разметка.

## 7. Внедрение и экономика (40 с)
- Пилот: 2–3 самых опасных участка, штатные IP-камеры (RTSP), один узел LinQ.
- Масштаб: калькулятор показывает число узлов на цех; правила и зоны настраивает специалист ОТ без программиста.
- Интеграции: вебхук → корпоративный мессенджер, СКУД, наряды-допуски.
- Импортонезависимость: российский ускоритель, локальный контур без облака.

## 8. Что дальше (20 с)
- Дообучение на кадрах заказчика из отметок оператора («ложное/подтверждено» = готовая разметка).
- Калибровка пола по 4 точкам → расстояния в метрах.
- Предиктивная аналитика по журналу, автоотчёты.

## Вопросы, к которым готовиться
- «Код писали с ИИ?» — да, как инструмент; архитектуру и решения объясняем сами, см. `docs/CODE_MAP.md`.
- «Почему несколько моделей, а не одна?» — включаются по участкам, экономят TPU; на LinQ — отдельные программы.
- «Как с ложными?» — подтверждение во времени, доля кадров, пороги, глубина для сближения, зоны и расписания, отметки оператора.
- «Где замеры на LinQ?» — скрипт готов; если стенд был недоступен — показать компиляцию и проверку квантования.
- «Одно нарушение — одна тревога?» — да: подтверждение во времени, склейка при смене ID трека; демо-ролик идёт по кругу,
  но повтор уже записанного нарушения новой тревоги не даёт — исходное событие просто снова становится активным.
- «Почему UR Fall, а не заводские видео?» — нужна открытая разметка с покадровыми метками; на заводских камерах человек крупнее, условия лучше.
